## 1. Пользователь и задача

Пользователь — антифрод-аналитик с ограниченным ресурсом ручных проверок.
Сервис ранжирует платёжные транзакции по score, показывает факты и объяснение модели,
помогает выбрать случаи для расследования. Баны и финансовые действия исключены из MVP.

Одна строка — транзакция. Момент score — время её совершения. Target — TX_FRAUD:
1 — fraud по авторскому синтетическому генератору, 0 — обычная операция в симуляции.
Это не подтверждение реального расследования. Вход — текущая транзакция и доступное прошлое.
Выход — score, версия модели и объяснение; вероятность не заявляется без калибровки.

Предыдущая идея возвратов заменена транзакционной постановкой. Преподаватель 23 октября
разрешил синтетику при акценте на интерпретируемости и задал роль LLM-объяснителя.
Он требует сначала литобзор на 5–6 страниц, затем согласование архитектуры.
Это разрешение направления, а не утверждение всех параметров паспорта или согласование команды заочно.

## 3. Сценарий и MVP

1. Загрузить поддерживаемый CSV или открыть демонстрационные операции.
2. Получить очередь по score при заданном бюджете проверок.
3. Открыть карточку: факты, исторические признаки, score, SHAP-вклады.
4. Прочитать текст локальной LLM и результаты автоматической проверки.
5. Выбрать случаи для расследования; выгрузить список и исследовательский отчёт.

MVP: простой baseline для сравнения, один бустинг LightGBM или CatBoost, SHAP,
шаблонное объяснение, локальная LLM-объяснитель, автоматические проверки, API и UI.
Конкретную LLM и окончательную архитектуру согласовать после литобзора.
Baseline — MLAF-4; здесь он не реализован. VPS/CI/CD — отдельные задачи.

LLM получает структурированные top-k признаки, значения, направления/величины вкладов
и шкалу объясняемого выхода; переводит их в текст. Предложен k=5, фиксируется до evaluation.
Top-k не выдавать за полное разложение score: учитывать остаток остальных вкладов.
LLM не решает, был ли fraud, не получает TX_FRAUD/TX_FRAUD_SCENARIO и не добавляет факторов.
Проверки: реальные названия/алиасы, покрытие top-k, знаки, числа и отсутствие новых факторов.
Понятность/полезность оцениваются отдельно; SHAP не доказывает причинность.
LLM-as-a-Judge — расширение в конце, не обязательный этап MVP.

Исключены: реальные санкции/платежи, streaming, несколько fraud-доменов, обучение своей LLM,
обязательные микросервисы и заявления о production-качестве на маркетплейсе.

## 4. Признаки, метки и leakage

Сумма и время известны при score. ID — ключи истории и дедупликации, не числовые
величины для первоначального классификатора. Исторические окна используют строго
event_time < current_time; будущие операции и агрегаты по всему файлу запрещены.
TX_FRAUD — только target. TX_FRAUD_SCENARIO — служебная offline-разметка:
оба исключены из входов детектора/LLM и обычных агрегатов.

Реального времени подтверждения метки нет. Принимаем моделируемый label delay 7 дней
для всех меток: это допущение исследования. На дату обучения используются лишь уже
созревшие по нему метки. Не выдавать event_time + 7 дней за наблюдаемый исходный столбец.

Проверять дубли ID, типы, пропуски, диапазоны и хронологию. Fit только на train;
validation/test/inference получают неизменные преобразования. Нет resampling в val/test.

## 5. Схема валидации и метрики для Review

Предложенные полуоткрытые интервалы; исходное время без указанной TZ:

| Назначение | Интервал |
|---|---|
| Прогрев исторических признаков | [2018-04-01, 2018-05-01) |
| Train | [2018-05-01, 2018-07-01) |
| Ожидание меток | [2018-07-01, 2018-07-08) |
| Validation | [2018-07-08, 2018-08-01) |
| Ожидание меток | [2018-08-01, 2018-08-08) |
| Test | [2018-08-08, 2018-10-01) |

Начальный эксперимент без переобучения в test. Модель/параметры и порог выбираются на
validation; затем фиксируются и открывается test. Метки последних событий test
станут доступны по допущению ещё через 7 дней. Илья ревьюит даты до MLAF-4.
Немаркированные прошлые события из периодов ожидания можно включать в историю признаков.

Сценарий — будущие операции, включая существующих клиентов. Поэтому group-disjoint
split не обязателен; пересечение клиента с его будущими операциями само по себе не leakage.
По возможности отдельно показать известные/новые сущности и размер подгрупп.

Основная метрика: recall при проверке 1% операций каждого дня. Для дня t выбрать
top ceil(0,01 × N_t) по score, посчитать общий recall за период. Tie — по TRANSACTION_ID.
1% — экспериментальный бюджет к утверждению, а не измеренная capacity аналитиков.
Дополнительная чувствительность — 2% и 5%. Top-K по заранее заданному бюджету не
является подбором порога по test.

Дополнительно: precision при том же бюджете, Average Precision
(average_precision_score — явно указанный метод расчёта PR-метрики), confusion matrix
при validation-пороге, доля fraud по периодам. Accuracy не критерий выбора.
Class weights/resampling определяются только по train, val/test сохраняют дисбаланс.
Сравнение: recall@1%, при равенстве AP, затем простота. Качество пока не измерено.

Затраты: C_review × K + C_miss × FN; отношения C_miss/C_review = 10, 50, 100
предлагаются как условные сценарии чувствительности. Реальных цен и доказанной экономии
нет. FP расходуют бюджет проверок и видны в precision@K; санкции в MVP не применяются.

## 6. Гипотезы и ограничения исследования

Главный вопрос: насколько локальная LLM верно и понятно вербализует SHAP относительно
шаблона? Верность — автоматические проверки; понятность/полезность — отдельный human-пилот.
Разделять development и evaluation по исходному кейсу. Подробный протокол/rubric — MLAF-2.
Дополнительная гипотеза: история улучшает приоритизацию относительно простого baseline.
Гипотезы о добросовестных возвратах на текущем наборе не проверяются.

Сценарий генерации не эталон SHAP: объясняется обученная модель.
Синтетика не подтверждает перенос на реальный marketplace. Польза LLM и рост
обоснованного доверия пока не доказаны. Разрешение синтетики не означает согласование архитектуры.
