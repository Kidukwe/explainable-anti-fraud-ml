# Границы и контракты первого спринта

Уже работает: GET /healthz → 200 {status: ok, service: antifraud};
GET /readyz → 503 {status: not_ready, reason: model_not_implemented};
GET /api/v1/metrics → 503 {status: not_available, metrics: null, reason: evaluation_not_run}.
GET / → operational dashboard; /docs и /openapi.json → реальный контракт.
Liveness контейнера использует /healthz; readiness пока намеренно отрицательная.

Ни /predict, ни фиктивной модели нет. До их реализации согласовать:

- единицу наблюдения, target, время события и время получения метки;
- имена/типы полей, missing/unknown, валюту/единицы, допустимые диапазоны;
- доступность каждой фичи к моменту score и исключение post-outcome leakage;
- response: score, threshold, model_version, feature_schema_version, request_id;
- ошибки 422, отсутствие модели 503, batch limits и latency budget;
- offline evaluation: dataset version, split boundaries, seed, prevalence, threshold,
  confusion matrix, ROC-AUC, PR-AUC (с методом расчёта), precision/recall/F1;
- explainability schema, ограничения интерпретации и отсутствие PII в логах.

Владелец ML-контракта — Tech Lead; API — Fullstack 1; UI — Fullstack 2;
MLOps проверяет artifact loading и эксплуатационные ошибки. Черновик не является
готовым API-контрактом предсказаний: принимается отдельным PR.

## ML → API → UI — черновик v1

Описанные эндпоинты оценки и получения операций пока не реализованы.

Цель v1 — выбрать операцию из согласованного датасета, получить реальную оценку модели через API и показать результат в UI.

Обучение выполняется отдельно от HTTP-запросов. При отсутствии модели фиктивная оценка не возвращается. Отсутствие XAI не блокирует показ реального результата.

### 1. Основные понятия

Операция — одна запись, которую оценивает модель. Её точный смысл — заказ, возврат или другая сущность — согласуется с ML-командой.

operation_id — уникальный идентификатор операции внутри активной версии датасета. В API передаётся строкой.

score — числовая оценка модели. Значение положительного класса, диапазон score и направление подозрительности определяет ML-команда. До согласования score нельзя называть вероятностью мошенничества.

threshold — порог принятия решения, выбранный ML-командой на validation-данных. UI получает его от API.

Для v1 приложение работает с одной активной версией датасета и совместимым с ней bundle модели.

### 2. Общая цепочка

1. UI запрашивает доступные операции.
2. Пользователь выбирает операцию.
3. UI отправляет её ID в API.
4. Backend находит запись в активном датасете.
5. ML-пайплайн преобразует данные и рассчитывает score.
6. API возвращает результат, порог и версии.
7. UI отображает ответ без самостоятельного перерасчёта.

Возможность оценки конкретной операции определяется согласованными правилами доступа и допустимости. Эти правила требуется уточнить до реализации.

### 3. Получение списка операций

Предлагаемый эндпоинт: GET /api/v1/operations

Он возвращает операции, доступные для выбора и оценки.

Пример ответа 200:

```json
{
  "dataset_version": "demo-v1",
  "items": [
    {"operation_id": "456"},
    {"operation_id": "457"}
  ]
}
```

Если датасет доступен, но подходящих операций нет:

```json
{
  "dataset_version": "demo-v1",
  "items": []
}
```

UI показывает «Нет доступных операций для оценки».

Пустой список не означает ошибку загрузки данных. Если датасет недоступен, API возвращает 503 с кодом dataset_unavailable.

Состав полей для отображения операций и ограничение размера списка согласуются с UI и ML-командой. Весь большой датасет одним ответом не возвращается.

#### Поля очереди — предложение для согласования

Источник полей — словарь FDH из PR №6. Состав требует review Кирилла и Ксюши.

| Поле API | Источник FDH | Назначение |
| --- | --- | --- |
| operation_id | TRANSACTION_ID | ID операции, в API передаётся строкой |
| event_time | TX_DATETIME | Время операции; часовой пояс не определён |
| amount | TX_AMOUNT | Сумма в условных денежных единицах, без обозначения валюты |
| customer_id | CUSTOMER_ID | ID синтетического клиента |
| terminal_id | TERMINAL_ID | ID платёжного терминала |

Требует согласования: очередь содержит уже рассчитанные score или оценка запускается после выбора операции? Порядок выдачи и лимиты списка пока не определены.

### 4. Запрос на оценку операции

Предлагаемый эндпоинт: POST /api/v1/predict

Тело запроса:

```json
{
  "operation_id": "456"
}
```

| Поле | Тип | Обязательное | Правила |
| --- | --- | --- | --- |
| operation_id | string | Да | Непустая строка; строка только из пробелов недопустима |

Число, null, отсутствие поля и пустое значение не принимаются как корректный ID. Неизвестные поля запроса отклоняются.

Перед проверкой длины пробелы по краям `operation_id` удаляются. Если результат пустой, запрос отклоняется.

UI передаёт ID. Поиск записи, подготовка признаков и вызов модели выполняются на backend.

### 5. Успешный ответ

HTTP 200.

Пример структуры ответа; все значения условные:

```json
{
  "request_id": "req-example-001",
  "operation_id": "456",
  "prediction_id": "pred-example-001",
  "score": 0.82,
  "threshold": 0.70,
  "model_version": "baseline-v1",
  "feature_schema_version": "features-v1",
  "dataset_version": "demo-v1",
  "explanation": {
    "shap": {
        "status": "unavailable",
        "reason": "xai_not_implemented"
    },
    "llm": {
        "status": "unavailable",
        "reason": "shap_unavailable"
    },
    "checks": {
        "status": "not_run",
        "reason": "llm_text_unavailable"
    }
}

```

| Поле | Назначение |
| --- | --- |
| request_id | Идентификатор запроса для поиска в логах |
| operation_id | Идентификатор оценённой операции |
| score | Реальная оценка загруженной модели |
| threshold | Порог из загруженного bundle |
| model_version | Версия модели, выполнившей расчёт |
| feature_schema_version | Версия схемы признаков |
| dataset_version | Версия датасета, из которого получена операция |
| explanation | Состояние доступности объяснения |
| prediction_id | Идентификатор конкретного результата оценки |

score и threshold должны быть конечными числами. Допустимые диапазоны фиксируются после определения смысла score.

UI показывает score, порог и версию модели. Округление применяется только для отображения.

Если UI показывает метку «подозрительная», правило её определения сначала согласуется с ML-командой. Предложение для обсуждения: при большем score подозрительность выше, а операция помечается при score >= threshold.

Оценка модели не является доказательством мошенничества.

shap, llm и checks находятся внутри объекта explanation успешного ответа. Они относятся к prediction_id, операции и версиям из этого ответа. Вложенные идентификаторы explanation_id и generation_id связывают SHAP, текст и проверки между собой.


### 6. Объяснение результата

В первой интеграции допустим ответ:

```json
{
  "explanation": {
    "shap": {
        "status": "unavailable",
        "reason": "xai_not_implemented"
  },
    "llm": {
        "status": "unavailable",
        "reason": "shap_unavailable"
    },
    "checks": {
        "status": "not_run",
        "reason": "llm_text_unavailable"
    }
}
```

UI показывает «Объяснение пока недоступно», сохраняя score и порог.

Другие возможные причины отсутствия объяснения должны быть перечислены при подключении XAI. Ошибка расчёта объяснения не должна скрывать уже полученную оценку.

#### Целевой формат SHAP → LLM → checks

Объяснение состоит из трёх отдельных частей: `shap`, `llm` и `checks`.
Отсутствие одной части не означает отсутствие остальных.

Все части относятся к одному результату оценки:
`operation_id`, `dataset_version`, `model_version`,
`feature_schema_version` и `prediction_id`.

`prediction_id` идентифицирует конкретный результат инференса.
`request_id` идентифицирует HTTP-запрос. Повторные запросы одной операции
могут относиться к разным результатам оценки.

Названия полей и правила идентификации требуют согласования.

##### SHAP

Описывает вклады признаков в конкретный выход модели.

Предлагаемые поля:

| Поле | Назначение |
| --- | --- |
| status | `ready`, `unavailable` или `failed` |
| reason | Код причины, если результат недоступен |
| method | Метод объяснения |
| method_version | Версия реализации или конфигурации объяснения |
| output_name | Какой выход или класс модели объясняется |
| output_scale | Шкала: например, raw margin или probability |
| base_value | Базовое значение в указанной шкале |
| output_value | Объясняемый выход в той же шкале |
| features | Список признаков: имя, значение, вклад |
| top_k | Число показанных признаков |
| remaining_contribution | Сумма вкладов остальных признаков |
| template_text | Детерминированный текст на основе вкладов |

Для `ready` обязательны данные объяснения, для остальных статусов — причина.
Числовые результаты должны быть конечными.

`base_value + сумма показанных вкладов + remaining_contribution`
должны совпадать с `output_value` в согласованной погрешности.

`output_value` не обязательно равен `score`: SHAP может объяснять выход
в другой шкале. Преобразование и направление вкладов фиксирует ML-команда.

Показываются только доступные при оценке признаки.
TX_FRAUD и TX_FRAUD_SCENARIO исключаются.
SHAP объясняет модель, а не причинность и не доказанный факт фрода.

##### LLM

Преобразует готовое структурированное объяснение в текст.
LLM не рассчитывает score и не принимает решение о мошенничестве.

Предлагаемые поля:

| Поле | Назначение |
| --- | --- |
| status | `ready`, `unavailable` или `failed` |
| reason | Код причины недоступности или сбоя |
| text | Сгенерированный текст, обязательный для `ready` |
| model_version | Идентификатор и версия LLM |
| prompt_version | Версия шаблона запроса |
| generation_id | Идентификатор генерации для связи с проверками |
| explanation_id | Идентификатор исходного SHAP-объяснения |

В SHAP-часть добавляется `explanation_id`.
LLM получает факты операции, согласованные признаки и их вклады,
шкалу выхода и остаточный вклад. Не получает offline-метки.

LLM не должна добавлять неподтверждённые факторы, менять числа
или утверждать причинность и доказанный фрод.

При недоступности LLM сохраняются score и готовый SHAP.
Для UI предлагается fallback на детерминированный `template_text`.
Fallback не выдаётся за текст LLM.

##### Автоматические проверки — checks

Проверяют конкретный сгенерированный текст относительно его источника.

Предлагаемые поля:

| Поле | Назначение |
| --- | --- |
| status | `passed`, `rejected`, `not_run` или `failed` |
| reason | Причина пропуска или технического сбоя |
| checker_version | Версия набора проверок |
| generation_id | Какая генерация проверена |
| explanation_id | Какое SHAP-объяснение использовано |
| items | Результаты отдельных проверок |

Каждый элемент `items` содержит код проверки, её статус и найденные нарушения.

Проверяются:
- соответствие названий признаков и разрешённых алиасов;
- числа и направления вкладов;
- покрытие согласованных top-k факторов;
- отсутствие новых факторов;
- необоснованные утверждения причинности или доказанного фрода.

`rejected` означает, что проверка выполнена и выявила нарушения.
`failed` означает технический сбой проверки.
`not_run` означает, что проверка не запускалась.

`passed` подтверждает прохождение перечисленных проверок,
но не гарантирует истинность текста или качество модели.

##### Отображение в UI

| Ситуация | Поведение |
| --- | --- |
| SHAP недоступен | Показать score и причину отсутствия объяснения |
| SHAP готов, LLM недоступна | Показать SHAP и шаблонный текст |
| LLM готова, checks passed | Показать текст с результатами проверок |
| checks rejected | Не показывать текст как проверенное объяснение; показать причину отказа и fallback |
| checks not_run или failed | Явно сообщить, что текст не проверен; по умолчанию показать fallback |

Отказ объяснения не отменяет успешно рассчитанный score.
Готовность первой score-интеграции MLAF-8 не означает готовность
полного объяснимого MVP MLAF-18.

### 7. Ошибки

Предлагается общий формат ошибки:

```json
{
  "request_id": "req-example-002",
  "error": {
    "code": "model_unavailable",
    "message": "Модель пока недоступна"
  }
}
```

code — стабильное значение для логики UI. message — пояснение для человека.

error.details — необязательный список ошибок отдельных полей запроса. Если подробностей нет, значение может быть null.

| HTTP | error.code | Когда возвращается |
| --- | --- | --- |
| 422 | validation_error | Запрос нарушает входную схему |
| 404 | operation_not_found | ID корректен, но операция не найдена |
| 503 | model_unavailable | Модель отсутствует или не загружена |
| 503 | model_incompatible | Bundle несовместим со схемой или активным датасетом |
| 503 | dataset_unavailable | Активный датасет невозможно использовать |
| 500 | internal_error | Непредвиденная ошибка обработки |

Для 422 предлагается дополнительно возвращать список ошибок полей:

```json
{
  "request_id": "req-example-003",
  "error": {
    "code": "validation_error",
    "message": "Некорректный запрос",
    "details": [
      {
        "field": "operation_id",
        "code": "required",
        "message": "Укажите ID операции"
      }
    ]
  }
}
```

Конкретные коды ошибок полей фиксируются при реализации схем.

Единый формат 422 потребует собственного обработчика в FastAPI: стандартный ответ фреймворка имеет другую структуру.

В ответы не включаются traceback, пути к файлам и исходные записи датасета.

Правила для запрещённых операций и соответствующий HTTP-статус согласуются отдельно после определения правил доступа.

### 8. Поведение UI

| Ситуация | Поведение |
| --- | --- |
| Получен непустой список | Дать выбрать операцию |
| Получен пустой список | Показать пустое состояние, не запускать оценку |
| Запрос выполняется | Показать загрузку |
| Оценка получена | Показать score, порог и версию модели |
| Объяснения нет | Показать явное сообщение о его недоступности |
| Получен 422 | Показать ошибку ввода |
| Получен 404 | Сообщить, что операция не найдена |
| Получен 503 | Сообщить о недоступности оценки |
| Ошибка сети или 500 | Сообщить, что запрос не удалось выполнить |

При выборе другой операции прежняя оценка очищается либо явно остаётся привязанной к прежней операции. Поздний ответ на старый запрос не должен заменять результат для новой выбранной операции.

Mock-ответы, если используются при разработке UI, явно обозначаются как демонстрационные и не выдаются за реальный инференс.

### 9. Передача модели из ML в API

ML-команда передаёт versioned bundle, содержащий:

- модель;
- необходимые преобразования данных;
- схему входа и признаков, включая типы и обработку missing/unknown;
- manifest с версиями и параметрами оценки.

Manifest фиксирует:

| Поле | Содержание |
| --- | --- |
| model_version | Версия модели |
| feature_schema_version | Версия схемы признаков |
| dataset_version | Версия согласованного датасета |
| target_definition | Что предсказывает модель и какой класс положительный |
| score_definition | Смысл score, диапазон и направление |
| threshold | Выбранный порог |
| decision_rule | Правило сравнения score с порогом |
| Артефакты и зависимости | Какие файлы и версии библиотек нужны для загрузки |

Точные имена дополнительных полей manifest и формат файлов согласуются с ML и MLOps.

API использует тот же preprocessing, что и offline-предсказание. Обучение и подбор порога внутри HTTP-запроса не выполняются.

Перед готовностью инференса backend проверяет загрузку bundle и совместимость его версий. Значения версий и порога в ответе берутся из фактически используемого bundle.

### 10. Состояние приложения

- /healthz сообщает, что процесс работает; отсутствие модели само по себе не делает процесс неработающим.
- /readyz возвращает 503, пока необходимые для инференса данные или модель недоступны.
- После успешной загрузки совместимого bundle и данных /readyz возвращает 200.
- Отсутствие XAI не блокирует readiness первой версии.
- Метрики качества не подменяются нулями или демонстрационными значениями. Пока evaluation не выполнена, сохраняется состояние недоступности метрик.

Форматы ответов уже существующих эндпоинтов изменяются только отдельным согласованным решением.

### 11. Проверка и границы приёмки MLAF-5

В MLAF-5 проверяются схемы и условные примеры сообщений.
HTTP-маршруты, модель и интеграция с UI здесь не реализуются.

Проверки схем:
- валидный и невалидный operation_id, отсутствие поля, лишние поля;
- готовый и недоступный SHAP, LLM и checks;
- согласованность статусов, количества признаков и идентификаторов;
- полный ответ оценки без объяснения;
- структура ошибок.

Сценарии unknown ID, недоступных данных/модели, пустого списка
и отказа объяснения разбираются walkthrough по примерам контракта.
Фактические результаты тестов и walkthrough указываются в PR отдельно.

Реальные HTTP 422/404/503, загрузка bundle и сравнение
offline → API → UI проверяются в MLAF-8.
Полная цепочка объяснений принимается в MLAF-18.

Для приёмки MLAF-5 необходимы:
- review Кирилла по ML-полям и архитектуре;
- проверка Ксюшей полей очереди и UI-состояний;
- решения по открытым вопросам либо явно зафиксированные блокеры;
- независимое одобрение, зелёный CI и merge по правилам проекта.

Описание сценария само по себе не подтверждает его проверку.
