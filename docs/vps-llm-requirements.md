## Основа оценки

В проверенном локальном bootstrap (SHA
`ff2ae3fa6ce7a13e81536eedaea86184d5d4582f`, ветка PR #3) есть FastAPI
и статический интерфейс. PR #3 ещё открыт; его содержимое не считается принятым в main.
Обученной ML-модели, inference API и реализации LLM ещё нет.
[Архитектура](architecture.md) предполагает один сервис, offline-обучение и
необязательную LLM вне обязательного пути приложения.
Зависимости задачи: MLAF-7 (bootstrap) и предварительная роль LLM из MLAF-2.
Соответствие локального bootstrap приёмке MLAF-7 отдельно не подтверждалось;
роль объяснителя уточнена по [паспорту MLAF-1 на проверенном SHA](https://github.com/Kidukwe/explainable-anti-fraud-ml/blob/99ebcdce906c551cd94fa1291c7a4b9cbb4f63cc/docs/mlaf-1/project-passport.md)
и [review Ильи](https://github.com/Kidukwe/explainable-anti-fraud-ml/pull/4#issuecomment-6428742968).
LLM вербализует структурированные top-k SHAP (предложено k=5), значения, знаки,
величины вкладов и шкалу выхода, с учётом остатка вкладов. Она не определяет fraud,
не получает target/служебный сценарий и не добавляет новые факторы.
LLM-as-a-Judge — расширение, не основной сценарий. Исследование — offline-пилот
на десятках/сотнях одноразовых генераций (оценка объёма из review, точное N — MLAF-2).
Главный вариант — заранее подготовленные и проверенные ответы для интерфейса.
Живая генерация и VPS рассматриваются только при отдельной потребности демо.
Модульный монолит остаётся инфраструктурной основой; окончательная архитектура
после литобзора и параметры рубрики ещё требуют согласования. Это не решение
команды о runtime, модели, размещении или расходах.

Все конфигурации ниже — инженерные оценки для небольшого учебного демо:
один процесс приложения, до 5 одновременных пользователей, небольшие запросы,
без обучения на VPS. Для LLM — одна генерация одновременно, контекст до
2048 токенов вместе с chat template и ответом, ответ до 256 токенов, квантованные веса Q4.
Это допущения для расчёта, а не согласованная нагрузка или доказанные минимумы.

## Прикидка мощностей

RAM/VRAM и диск указаны в GiB. Диск — общий ориентир на ОС, окружение,
артефакты и ограниченные логи; размер датасета в оценку не включён.

| Сценарий | CPU | RAM | GPU / VRAM | SSD | Latency: предварительный ориентир | Основание и ограничения |
|---|---|---|---|---|---|---|
| Только текущий API и интерфейс | 1–2 vCPU | 2 GiB | Не требуется | 20 GiB | Цель p95 ≤ 300 мс для простых API-ответов | Оценка для текущего bootstrap; это не latency ML |
| Приложение с будущей табличной ML-моделью и сохранёнными результатами | 2 vCPU | 4 GiB; при тяжёлом bundle рассмотреть 8 GiB | Предварительно не требуется | 30–40 GiB | Цель p95 ≤ 1 с на одиночный score без online SHAP и LLM | Оценка; зависит от preprocessing, модели, размера bundle и нагрузки |
| Отдельная offline LLM около 4B, Q4, CPU | 4–8 ядер или vCPU для пробы | 8 GiB как нижний ориентир, 16 GiB предпочтительно | Не обязательна | 15–20 GiB свободно на существующем ПК; около 40 GiB общего диска для отдельного хоста | Секунды–минуты на ответ допустимы только для offline-сценария; скорость неизвестна | Оценка для одного задания и короткого контекста; shared vCPU не равно физическим ядрам |
| Та же LLM около 4B с ускорением на уже доступной GPU | 4–8 ядер | 16 GiB | 6–8 GiB VRAM как ориентир для пробы | Как для CPU-варианта | Цель для обсуждения: первый токен ≤ 3 с, ответ ≤ 30 с | Не гарантия; нужны совместимый runtime, проверка размещения весов, KV-cache и замеры |
| Эксперимент с LLM 7–8B, Q4 | 8 ядер для CPU-пробы | 16–32 GiB | Не обязательна; для полного GPU-размещения ориентир 10–12 GiB VRAM | 20–30 GiB свободно на ПК либо 50 GiB общего диска хоста | Не назначать интерактивный SLA до замеров | Экстраполяция по классу размера, конкретная модель не выбрана; вне базового объёма S1 |

Числа CPU/RAM/VRAM/SSD и цели latency предложены автором документа, а не взяты
из обещаний производителя. Все показатели производительности: **не измерено**.
Apple Silicon использует общую память: нельзя считать системную RAM и VRAM
двумя независимыми доступными объёмами.

Для LLM-кандидата можно обсудить Qwen3-4B-GGUF Q4_K_M: официальный
[список файлов Qwen](https://huggingface.co/Qwen/Qwen3-4B-GGUF/tree/main)
показывает весовой файл около 2,5 GB (десятичные единицы). Это размер файла,
не полная RAM/VRAM процесса. Это кандидат для пробы, не утверждённый выбор команды; веса не скачивались.
[Карточка Qwen3-4B](https://huggingface.co/Qwen/Qwen3-4B) описывает режимы
thinking/non-thinking; для пробы предложен non-thinking. Проверка русских
объяснений выполняется после подготовки рубрики MLAF-2, а не считается уже выполненной.
Для одной пробы выбран runtime-кандидат llama.cpp с Metal; mlx-lm не запускаем
параллельно для сравнения в этой задаче. Перед пробой зафиксировать commit/build,
Metal backend, revision/hash GGUF и встроенного Qwen3 chat template.
В llama-server включить Jinja template; в запросе `/v1/chat/completions` задать
`chat_template_kwargs: {"enable_thinking": false}`. Поддержку проверить по `--help`
зафиксированного build и логам шаблона; скрытие reasoning в UI не отключает thinking.
[Документация runtime](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
описывает этот параметр. Runtime сейчас не установлен и команды LLM не выполнялись.

Для памяти считать веса + KV-cache + рабочие буферы + ОС/приложение + запас.
Контекст, параллельные генерации и runtime меняют итоговый объём; размер весов
не доказывает, что модель поместится. Для приложения учитывать копию ML-модели
на каждый worker: это отмечено в
[документации FastAPI](https://fastapi.tiangolo.com/deployment/concepts/).
Стартовая оценка предполагает один worker и резерв примерно 25–30% RAM.
Для диска учитывать текущую и предыдущую версии bundle/image, временные файлы,
ограничение логов и резерв свободного места около 20%; большие данные считать отдельно.

## Варианты размещения

| Вариант | Что потребуется | Когда рассматривать |
|---|---|---|
| Локальное приложение и сохранённые результаты | Уже доступный компьютер; новая покупка не требуется при достаточных ресурсах | Первый вариант для учебного демо; результаты ещё предстоит получить |
| Небольшой VPS для API, LLM отдельно offline на ПК | Ориентир VPS: 2 vCPU / 4 GiB RAM / 30–40 GiB SSD; ПК по строке 4B | Если команда подтвердит необходимость постоянного удалённого доступа |
| **Основной: заранее подготовленные ответы LLM** | Offline-генерация и диск для результатов; постоянно загруженная LLM не нужна | Текущий пилот вербализации SHAP; явно обозначать сохранённый ответ и версию |
| API и живая LLM на одном хосте | Суммарный ресурс обоих процессов, изоляция нагрузки и повторные замеры | Только после подтверждения роли LLM и интерактивной потребности; сейчас не рекомендуется выбирать конфигурацию для покупки |

Практическое предложение: сейчас использовать этот Mac для локального
bootstrap и дальнейшей интеграции, проверяя потребление памяти после появления
bundle. По паспорту FDH каталог содержит 183 файла, 107 121 710 байт raw
(около 107 МБ); около 1,75 млн строк — сведения авторской документации,
не наш пересчёт. Полный набор в этой задаче не загружался. Для компактных
числовых признаков обучение одного бустинга предварительно выглядит возможным
на 8 GiB, но raw-размер не равен RAM: копии таблиц, история и SHAP увеличивают пик.
Это оценка, не доказательство размещения. Обучение, SHAP и LLM выполнять последовательно,
освобождая предыдущий процесс/артефакты в RAM, не одновременно.
В текущем pyproject/lock предусмотрен CatBoost; он принят для ресурсного сценария
этого документа. Паспорт допускает LightGBM или CatBoost: окончательный выбор — ML-команде.
LightGBM здесь не установлен/не проверен; при его выборе отдельно согласовать
зависимости и повторить оценку, не выдавать проверку CatBoost за проверку LightGBM. LLM 4B Q4 оставить кандидатом
для отдельной ограниченной пробы на этой машине, а не считать готовым решением.
На 8 GiB запас тонкий: веса, KV-cache, буферы, macOS и браузер могут вызвать своп.
Первая проба: одна генерация, контекст 2048 суммарно, выход до 256 токенов;
закрыть тяжёлые приложения, не запускать обучение/SHAP вместе с LLM.

До запуска фиксируем предложенный критерий технической пробы: после одного
прогрева 10 одинаково подготовленных development-кейсов проходят без OOM,
роста swap used относительно исходного значения и без увеличения swapouts;
каждый полный ответ укладывается в 120 с. Это предварительный порог для offline,
не SLA и не измеренный результат; Илья подтверждает его до пробы. Swap проверить
через `sysctl vm.swapusage` и `vm_stat` до/после и наблюдением во время серии;
сохранить вывод и состояния memory pressure. Фоновую активность ОС отметить;
неясный результат означает «не подтверждено», а не успешную пробу.
При нарушении любого порога остановить 4B-пробу: перейти на кандидат 1,5–2B Q4
либо другой уже доступный ПК с 16 GiB+, повторить ту же проверку. Не покупать GPU.
Качество меньшей модели оценить отдельно по MLAF-2: технический успех его не доказывает.

Для нового окружения установить uv по [официальной инструкции](https://docs.astral.sh/uv/getting-started/installation/)
(например, `brew install uv`, если Homebrew уже используется), открыть новый терминал,
записать `uv --version`, использовать Python 3.12 и `uv sync --frozen`.
Исторический `/tmp`-путь в неизменяемом логе — свидетельство прошлой проверки,
а не инструкция постоянной установки. В этой правке установка не выполнялась.

Повторить функциональную проверку на SHA bootstrap выше (он содержит
`scripts/smoke.py`, которого пока нет в main). Сервер — в первом терминале,
smoke — во втором; после проверки остановить сервер через Ctrl+C:

```bash
.venv/bin/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
.venv/bin/python scripts/smoke.py --base-url http://127.0.0.1:8000
```

В фактическом логе использован свободный динамический localhost-порт и
наследуемый socket через `--fd`; проверены те же endpoints. Это smoke, не
нагрузочный тест. Приложение после проверки остановлено.

Offline означает генерацию отдельно от HTTP-запроса; запуск без сети возможен
после предварительной подготовки локальных весов и runtime. Для воспроизведения
сохранить revision и SHA-256 весов, версию runtime, prompt/template, параметры
генерации, seed, версии ML-модели и входных обезличенных артефактов, ответ,
статус ошибки и результат review. Для пилота зафиксировать один профиль non-thinking: `temperature=0.7`,
`top_p=0.8`, `top_k=20`, `min_p=0`, `seed=42`, `max_tokens=256`,
`chat_template_kwargs={"enable_thinking": false}`, `repeat_penalty=1.0`,
`presence_penalty=0.0`, `frequency_penalty=0.0`. Полный эффективный профиль
и порядок samplers зафиксировать по выбранному build. Профиль следует non-thinking
рекомендациям карточки Qwen, а не обещает детерминизм. Не менять его между
сравниваемыми прогонами и не подбирать по evaluation. Сохранить полный запрос,
эффективные параметры и ответы; автоматические проверки верности сравнивать
на одинаковых кейсах. Seed сам по себе не гарантирует побитового совпадения.
Изменение модели/runtime/template/профиля образует отдельную серию эксперимента.
Артефакты хранить вне Git по правилам проекта; объём и retention согласовать.
Без подготовленных ответов UI должен показывать отсутствие результата.

## Замеры и блокер

[Запись о недоступности и статусе измерений](evidence/s1/vps-llm-not-measured.md).
VPS отсутствует по описанию задачи. Характеристики текущего Mac подтверждены
инвентаризацией выше; готовность к LLM не подтверждена: runtime не обнаружен
в проверенных местах, доступная память и запуск весов не проверены.
Бюджет неизвестен. Требования не подменяются историческими
smoke-проверками bootstrap: они не измеряли LLM и будущий ML inference.

После появления окружения записать CPU/ядра, RAM, GPU/VRAM, ОС, свободный диск,
версии runtime/драйвера, SHA кода, hash весов, контекст, потоки и offload.
Сохранить точные команды, stdout/stderr и exit codes. Для LLM отдельно измерить
загрузку, prompt processing, generation tokens/s, пик RAM/VRAM и полное время
ответа на одинаковых обезличенных примерах. Холодный запуск отделить от прогретых.
[llama-bench](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md)
поддерживает повторения и JSON; его throughput не включает tokenization и sampling
и не заменяет end-to-end latency. Точные команды подобрать под зафиксированную
версию runtime; в этом черновике исполняемый протокол замеров не подготовлен.
Для API будущие p50/p95 считать на согласованной нагрузке, отдельно от LLM.
