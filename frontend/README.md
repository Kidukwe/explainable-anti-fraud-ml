# Frontend — очередь операций и карточка проверки

Учебный интерфейс MLAF-6 на React и Vite.

Все операции и ответы демонстрационные. Реальная модель, LLM,
SHAP-артефакты и API операций не подключены.

## Текущий статус

React-интерфейс запускается отдельно через Vite.

FastAPI пока обслуживает прежний интерфейс из backend/static.
Текущий Dockerfile не собирает новый frontend.

Интеграцию React-интерфейса с основным сервисом необходимо
согласовать с владельцем backend. Этот пункт приёмки ещё не закрыт.

## Требования

- Node.js 22 и npm.
- Команды выполняются из папки frontend.

## Локальный запуск

Из корня репозитория:

```bash
cd frontend
npm ci
npm run dev
```

Открыть http://127.0.0.1:5173/.

Если порт занят, использовать адрес из терминала Vite.
Для остановки сервера нажать Ctrl+C.

## Тесты и сборка

```bash
npm test
npm run build
```

Дополнительные команды:

```bash
npm run test:ui
npm run test:ui:watch
npm run preview
```

- npm test и npm run test:ui запускают один набор тестов Vitest.
- test:ui:watch запускает тесты в режиме наблюдения.
- build создаёт сборку в frontend/dist.
- preview позволяет открыть собранный интерфейс локально.
  Адрес по умолчанию: http://127.0.0.1:4173/.
  Точный адрес выводится в терминале.

Preview не является production-развёртыванием.

## CI

В .github/workflows/ci.yml добавлена проверка
Frontend tests and build:

1. npm ci
2. npm test
3. npm run build

Проверка запускается для PR и push в main.
Обязательность проверки для merge настраивается владельцем
репозитория отдельно.

По приложенным результатам локально прошли 13 тестов
и production-сборка. Проверки CI также прошли после добавления job.

Компонентные тесты не заменяют ручную проверку приложения,
сверку с контрактом и независимое review.

## Проверка очереди и карточки

1. Запустить приложение.
2. Убедиться, что видны demo-баннер, очередь и вкладки.
3. Нажать на операцию № 10001.
4. Проверить открытие карточки, сумму, заказ и покупателя.
5. Закрыть карточку крестиком.
6. Проверить поиск по номеру операции и заказа.
7. Проверить вкладки и фильтр статуса.
8. Ввести отсутствующий номер и проверить пустой результат поиска.
9. Проверить открытие и закрытие демонстрационных окон заказа и товара.
10. Проверить CSV-экспорт текущей отфильтрованной выборки.
11. Проверить интерфейс на ширине 1280 px и около 390 px.
    Переключатель сценариев не должен перекрываться sidebar.
12. Проверить доступность переключателя с клавиатуры.

Шаги выше являются инструкцией, а не утверждением,
что все проверки уже выполнены.

## Проверка mock-сценариев

Использовать переключатель «Демо: сценарий проверки».

При смене сценария карточка закрывается. Для всех вариантов,
кроме пустой очереди, нужно повторно открыть операцию.
Для просмотра результата может потребоваться прокрутка карточки.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Загрузка | Отображается «Проверяем операцию…». Состояние специально остаётся загрузкой. |
| Пустая очередь | Отображается «В очереди нет операций», карточка скрыта. |
| Ошибка сети | Отображается ошибка и кнопка «Повторить». Повтор снова возвращает ту же mock-ошибку. |
| Модель недоступна | Отображается отдельное сообщение о недоступности модели. |
| Готовый ответ — mock | После искусственной задержки видны блоки score, SHAP, LLM и checks, а также тестовый текст объяснения. |
| Объяснение отсутствует | Отображается отсутствие текстового объяснения. |
| Отказ проверки — mock | Отображаются отказ проверки ответа и демонстрационная причина. Это не обвинение покупателя. |

Пустой результат поиска и сценарий пустой очереди проверяются отдельно.
В сценарии пустой очереди счётчики sidebar пока показывают
размер статического демонстрационного набора.

Искусственная задержка mock-запроса составляет 350 мс.
Это не измерение времени работы модели.

Все текущие mock-ответы содержат score: null и shap: null.
Отображение заполненного числового score и SHAP этими сценариями
не подтверждается.

## Защита от старого ответа

Ручная проверка:

1. Выбрать «Готовый ответ — mock».
2. Открыть первую операцию и дождаться результата.
3. Выбрать другую операцию.
4. Убедиться, что старый результат исчезает сразу,
   а для новой операции сначала показывается загрузка.

Автоматические тесты дополнительно проверяют:

- Запрос А, затем запрос Б; ответ Б приходит раньше ответа А.
  Поздний ответ А не заменяет результат Б.
- Ответ с чужим operationId не отображается.
- Старый сценарий той же операции не заменяет новый результат.
- Кнопка «Повторить» запускает повторный запрос.

Ручное переключение с фиксированной задержкой само по себе
не доказывает правильность обработки обратного порядка ответов.

## Структура frontend

- src/main.jsx — очередь, карточка, вкладки и управление сценариями.
- src/tab.json — строгая JSON-конфигурация вкладок.
- src/data.js — демонстрационные операции.
- src/mockScenarios.js — демонстрационные состояния проверки.
- src/OperationCheck.jsx — получение и отображение mock-ответа.
- src/utils.js — фильтрация, форматирование и CSV.
- src/style.css — оформление и адаптивная компоновка.
- tests/operation-check.test.jsx — компонентные тесты.
- vitest.config.js — конфигурация тестов.

Вкладки содержат id, title и content.
Поле content хранит строковый ключ компонента,
который разрешается через реестр компонентов.

## Границы mock-данных и контракта

Операции, суммы, покупатели, товары и бизнес-статусы заданы
вручную для демонстрации.

Время обработки не измерялось.
Показанные статусы операций не являются результатами
подключённой реальной модели.

Внутренние поля mock-ответов:

| Поле | Назначение |
| --- | --- |
| operationId | Привязка ответа к операции |
| result.score | Блок «Score модели» |
| result.shap | Блок «SHAP — вклады признаков» |
| result.explanation | Блок «LLM — текстовое объяснение» |
| result.checks.status | Статус проверки ответа |
| result.checks.reason | Причина отказа проверки |
| error.message | Сообщение об ошибке |
| error.canRetry | Доступность повторного запроса |
| result.isMock | Признак демонстрационного результата |

Это внутренний формат демонстрации, а не утверждённый API-контракт.

docs/contracts.md содержит требования к будущему контракту,
но не подтверждает согласование всей схемы предсказаний.

Для приёмки необходимо указать конкретную версию draft-контракта
и сверить:

поле контракта → поле mock-ответа → место в UI.

Поля threshold, model_version, feature_schema_version и request_id
нужно согласовать с владельцем контракта. Произвольно добавлять
их и заявлять совместимость нельзя.

Score не обозначается вероятностью без определения шкалы.

## ENVIRONMENT — ещё не реализовано

Единый параметр ENVIRONMENT=demo|production пока не подключён.
Текущее приложение всегда использует демонстрационные источники.

Установка ENVIRONMENT=production сейчас не отключает mock-данные
и не означает готовность production-интеграции.

После согласования с владельцем backend требуется реализовать:

- demo: mock-операции, переключатель сценариев и заметную маркировку.
- production: отключённые mock-источники и инструменты демонстрации,
  работа с согласованным реальным API.
- При отсутствии API или модели в production — состояние
  недоступности без подстановки mock-ответа.
- Неизвестное значение ENVIRONMENT — явная ошибка конфигурации.
- Единый источник конфигурации окружения.
- Проверки обоих режимов и отсутствие mock-fallback в production.

Команды запуска обоих режимов и настройки Docker/Compose
нужно добавить после реализации и фактической проверки.

## Доказательства проверки и приёмка

Для ручных проверок приложить к PR:

- commit SHA и дату;
- имя проверяющего;
- браузер и размер окна;
- шаги проверки;
- ожидаемый и фактический результат;
- скриншоты или короткое демо;
- актуальный вывод npm test и npm run build.

Непроверенные пункты отмечать «не проверено».

Для общего Done ещё требуются интеграция со штатным сервисом,
режимы окружения, сверка с draft-контрактом и независимая
проверка Алиной.

Зелёный CI и AI-review не заменяют независимую приёмку участником.
